# Add-ons: what to expect of each agent app

An add-on is how what you do on a page gets back into the conversation that made the page, by itself. This page says what every add-on does, which routes a click tries, what to expect in each agent app, and what It does not do. [Agents](agents.md) has the table of which add-ons are proven, and what that rests on.

## What every add-on does

- It is a plugin to the agent app's unmodified release. No agent app is forked or patched, and It never wraps or replaces the command you start an agent app with.
- It is installed with the app's own command for add-ons where the app has one (Claude Code, Codex, Pi, OpenClaw). OpenCode has none, so its plugin and the skill are copied into the folder OpenCode loads from, and Hermes's are copied and then switched on with Hermes's own command.
- In every app the agent is shown the skill under one name, `it`. Claude Code and Codex list a skill that is inside a plugin under the plugin's name as well, as `it-bridge:it`. So for those two the plugin carries the hooks alone, and the skill is copied beside your own skills, into `~/.claude/skills/it` and `~/.codex/skills/it` (or wherever `CLAUDE_CONFIG_DIR` and `CODEX_HOME` say). A skill of that name that you had there already is yours: it is kept beside the new one under another name, and one you have changed since is left where it is when the app is disconnected.
- In Claude Code, Codex, Pi and OpenCode the add-on also tells the agent when a page is the answer, at the start of a conversation: in Claude Code and OpenCode as one paragraph added last to the agent's own instructions, in Pi as one more of the guidelines it gives its agent, and in Codex as what its hook for the start of a session gives. The skill says how to use It, and an agent reads it only once it has decided to. Its short description alone did not bring a model to that often enough: asked for a game or for a report, it answered in the chat. With the paragraph, the same model built the page for all thirteen of thirteen such requests, and answered all twelve plain ones in the chat, one that asked for a table among them. The paragraph is this, and nothing else is added: "It is set up on this machine: a two-way workspace that you custom-make for the user, on any screen they own. You build the interface the task calls for as a page, what the user does on it comes back to you, and you answer on the page. Whenever the user is to see, use, play, choose, fill in or decide on something, build it there and do not write it into the chat. Load the skill named `it` before the first page. A plain answer to a plain question stays in the chat." It goes when the app is disconnected. In Claude Code it is given only to an agent that has a shell and the skill, so not to the helpers a conversation starts for a search. The counts are of Claude Code with two of Anthropic's larger models, each given every request once. Its smallest model built the page for twelve of the thirteen, and for none of the plain ones. In Pi and OpenCode the paragraph is seen to be among the agent's instructions, and has not been counted in that way. Hermes and OpenClaw are told nothing this way yet: there the skill's description is all an agent has to go by.
- No add-on asks the connector through a proxy, whatever `HTTP_PROXY`, `HTTPS_PROXY` or a variable like them names where the agent app was started. What an add-on asks names a conversation and brings back what you did on a page, and the connector is on the same machine, so none of it is for a proxy to see. The add-ons for Pi, OpenCode and OpenClaw open a connection of their own for each question, to the socket in It's folder or, on Windows, to the connector's port on the machine itself. Hermes's does the same, and Codex's hook is the `it` command, which asks as it always does. Claude Code gives an add-on no connection of its own: over the socket it sends nothing through a proxy, and over a port it sends what an add-on asks through the proxy its environment names. So on Windows, in a Claude Code that was started with a proxy named, the add-on asks nothing and a click waits in the inbox, unless `NO_PROXY` or `no_proxy` lists `127.0.0.1` or `*`. Add `127.0.0.1` there and clicks arrive by themselves again.
- Each installation is written down with every file it wrote, so that only those files are ever replaced or removed. A file that was already there and is not It's is kept beside the new one, with `.set-aside-by-it` added to its name. An interrupted file replacement keeps a record of both the old and new contents, so connecting or disconnecting again recognises either. If a first copied installation stops before recording any files, disconnect can clear the attempt once every add-on file is confirmed absent from its recorded destination. If an installation record cannot be read, It leaves the add-on and the record in place until you restore the record.
- For Claude Code, Codex and OpenClaw, It refuses to replace or remove a plugin registered under its name unless this installation owns it. For Claude Code and Codex it checks the marketplace too, and leaves it alone if it contains another plugin. Setup keeps its marketplace files readable while refreshing them, so an interrupted refresh can be retried or disconnected. Files outside the current package are moved out of its source folder before installation, so the app cannot load obsolete commands or hooks. They are kept beside that folder under `addons/<app>.set-aside-by-it-<suffix>`, including any files you added there. An older installation record without saved profile settings is checked against the current profile, with the same ownership checks. Setup explains which app commands let you inspect and resolve a conflict. An add-on from another It folder stays with that folder while it has the installation on record.
- `it setup` installs an add-on only into a version of the app that is no older than the oldest one the add-on was tried with. It says which version it needs where the one it finds is older, and installs nothing there. Installation does not prove that the running app loaded the add-on. The Machines page and `it status` separately report the loaded build and its delivery APIs. An add-on that reports a missing API or a different build needs attention; update the app or run `it setup`, then restart the app as the status says. With no recent runtime report, the status is unverified, not incompatible. The app may simply be closed. Older add-ons can still deliver through the local API, but cannot prove their loaded capabilities.
- A page belongs to the conversation that made it, until another one takes it. `it create` under an id that is another conversation's page publishes nothing and says whose page it is: two conversations that each chose the same id would otherwise end with one page, and the first would go on telling its person to press a button it never hears of again. Whoever says "show me the board again" the next day is talking to the conversation in front of them, and that conversation takes the page, with `it open`, which brings it up as it is, or with `it create --take`, which replaces it; the command's answer says that the page changed hands. `it update` from another conversation changes what the page shows and leaves it where it is, and says so, unless it is given `--take`. A page also moves when the machine that made it has left or was revoked: it goes to whoever publishes it next, or to the machine that next takes a click of it for its conversation. And a page made in a thread of T3 Code goes with the thread when you switch the thread to another agent app, to the conversation the thread runs from then on: [T3 Code](#t3-code) says how.

## The order a click tries

A click is stored before anything tries to deliver it, and then tries these routes in order, stopping at the first that works:

1. **The add-on, live.** The add-on inside the conversation that owns the page puts the click into it now, or at the agent's next step if it is busy.
2. **The thread in T3 Code**, for a conversation that is held in one: [T3 Code](#t3-code) says how. T3 Code starts a turn in the thread and shows it there.
3. **The app's own queue**, where it has one. Codex has, and Codex's is the only queue It uses. It is used for a conversation that some Codex on the machine has open and that is in no thread of T3 Code. Such a Codex takes a queued message by itself: at once when it is idle, and when its turn ends when it is not.
4. **Reopening the conversation**, where Auto-wake is on for the agent app on that machine, as it is unless you have turned it off: [below](#a-conversation-that-has-been-closed) says how. A Codex conversation that no Codex has open goes this way too, and nothing is put in its queue: a queued message would wait there until the conversation was opened and a turn of it had ended.
5. **The inbox.** Everything else waits, in view: the site shows it, and the agent takes it with `it wait`.

None of these routes is tried for an agent app you have not connected. A click on a page it made waits in the inbox.

An add-on that cannot deliver a click leaves it in the inbox, and the site does not say why in every such case.

Delivery is at least once, and every click carries a stable id so that an agent can tell a repeat. In one case a click may be seen twice, with the same id: where It was stopped by a crash after Codex's queue took the click and before that was written down. Where what became of a click is not known, the site says so.

## What to expect in each agent app

It has add-ons for Claude Code, Codex, Pi, OpenCode, Hermes Agent and OpenClaw, and it reaches T3 Code through two of them. `it setup` asks for these versions or later:

| Agent app | The oldest version `it setup` installs into |
|---|---|
| Claude Code | 2.1.287 |
| Codex | 0.160.0 |
| Pi | 0.82.0 |
| OpenCode | 1.18.32 |
| Hermes Agent | 0.20.1 |
| OpenClaw | 2026.9.6 |

### Claude Code

When the conversation is idle, a click starts a turn. While a turn runs, the click is attached to the next tool result, so that nothing is interrupted, and it starts a turn when that one ends if no tool ran.

A click that starts a turn shows in the conversation as one short line: the page, what was done, and the action's id, as in `[It] "Chess" (chess): move, with details [action …]`. A thread in T3 Code and Codex's own queue are given the same line where they are not given the mark `[It]` alone, which [T3 Code](#t3-code) and [Codex](#codex) say more of. It stands there as your own message, which is the one way Claude Code shows a message from an add-on as it is, with no lines of its own around it. Nothing the page sent is put into that line: it holds the page's title, as the agent that made the page gave it and inside quotation marks that the title cannot close, the action's name, and nothing of what the action carried. Claude reads what the action carried with `it action`, where it arrives as data and not as something you said.

The add-on needs Claude Code 2.1.287 or later, with mods turned on. There is no other route for an older Claude Code, or for one where mods are turned off: a click waits in the inbox there.

### A conversation that has been closed

It reopens a conversation that has been closed, so that what you do on a page it made is acted on while you are away from the machine. This is Auto-wake. It is on for each agent app from when you connect it on a machine, and setup says so when it connects one. You turn it off, and on again, for each agent app on each machine by itself: on the site's Machines page, with the Auto-wake switch under the app. What you have turned off stays off, and connecting the app again does not turn it back on. Where it is off, "Wake it" on a page whose click nobody has taken turns it on as the switch does. Only a browser paired as yours can turn it on. A machine cannot, so an agent does not switch it on for itself by using the `it` command, nor by connecting its own app afresh. A machine that was set up with an It from before Auto-wake came on by itself keeps its switches as they were. That guards against its being done by the way, and is not a wall against an agent that sets out to: [every machine can pair a browser as yours](what-it-protects.md#every-machine-can-pair-a-browser-as-yours), and an agent runs as you on its machine. Turning it on also reopens conversations for what you did in the day before, oldest first, so a click that went unanswered an hour ago is acted on. A click that had been waiting longer than a day by then stays in the inbox, so that turning it on does not run your agent on answers you gave long ago. It is not offered for a machine that runs Windows yet: there the switch is absent, and what you do on a page waits until its conversation is open again.

With it on, a click for a conversation that is not listening is given at once to the agent app's own command for carrying a conversation on without a window. It knows which conversations are listening, since an open one asks for its clicks every second, so nothing is waited for but a third of a second that lets a few things done together go together, and, where three conversations are already running because It reopened them on that machine, a place among them. The command is run in the folder the conversation was held in. The click is its message, given on the command's input and never on its command line. The conversation then runs as it would with you there, except that nobody is watching, and it uses your account with that app as any turn does. It is told so in a few lines after the click: that nothing can be approved for it, how to run `it`, and to say so on the page, and mark the action as failed, where it cannot do what was asked. When you open the conversation again, the turn is in it.

| Agent app | What It runs | What the conversation may do by itself |
|---|---|---|
| Claude Code | `claude --resume <id> --print` | What it could do the last time you had it open. It is reopened in the permission mode you last held the conversation in, where that mode asks nobody: one you held with full access, in T3 Code say, is reopened with full access. One you held in the mode that asks is reopened with `it` and whatever your own settings allow, and anything else it tries is refused |
| Codex | `codex exec resume <id>` | Run in Codex's sandbox for a workspace, with the network allowed and It's own folder writable, which is what `it` needs. So it can write in the conversation's folder and in It's folder, `~/.it`, which holds It's own program as well: the sandbox keeps it out of the rest of your files, and not out of It |
| Pi | `pi --print --session <id>` | Whatever it does in a window: Pi does not ask before it runs a command |
| OpenCode | `opencode run --session <id>` | Whatever your OpenCode settings allow without asking |
| Hermes Agent | `hermes chat --resume <id> --query-file -` | Whatever your Hermes settings allow without asking |

All five have been run this way against the real programs on Linux: Claude Code and Codex with their own models, and Pi, OpenCode and Hermes with a model reached through OpenRouter. None has been run this way on Windows or macOS. OpenClaw has no such switch: its conversations live in its gateway, which is not closed.

The conversation's app profile is recorded locally when it publishes a page. Codex's hooks record it too. Resume commands, Codex's queue, and transcript and lock lookups use those recorded paths: `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`, `HERMES_HOME`, and OpenCode's XDG config, data, state and cache directories with `OPENCODE_CONFIG_DIR` and `OPENCODE_CONFIG`. Defaults are recorded too, and an unset optional override stays unset. These paths stay on the machine and are not included in runtime reports or usage counts. Credentials and inline configuration are never copied into this record. A recorded profile that is missing or removed, or OpenCode inline configuration, blocks automatic reopening instead of using the service's other profile. Conversations recorded before profiles were kept continue to use the service's environment until they report or publish again. Open the conversation in its own profile and publish its page again to refresh the record.

The command is started by It's background service, which the system starts with almost nothing of what your shell has. So on Linux and macOS the service asks your shell, when it starts and every few minutes while conversations are being reopened, what it would give a program: it starts your shell the way a terminal does, which runs your shell's own files, and reads what comes out. Whatever your shell exports that the service lacks is added for the agent apps it runs, and the folders of your shell's PATH after the service's own. That is how an agent app that takes its key or its proxy from a variable in `~/.profile`, `~/.bashrc` or `~/.zshrc` can be reopened. Nothing the service already has is changed, and none of it is written anywhere or leaves the machine. A shell that does not answer in eight seconds is given up on, and the apps then get what the service has; `IT_SHELL_ENV=off` in the service's environment keeps your shell from being asked at all, and the service has it there when it is set where `it setup` or `it service install` is run. On Windows the service already has your account's variables.

**Everything waiting goes in one message.** A conversation reopened for five clicks is reopened once, and reads all five, up to eight at a time. The oldest clicks go first, with a place kept for the person's oldest click if only timer clicks would fit. That click can pass older timer clicks, which stay waiting for the next turn. It checks closed conversations in successive groups, so a conversation that stays busy cannot keep another out of the inbox indefinitely.

**A conversation is reopened only so often.** Ten times at once, and then once more for every twenty seconds that pass, which a person using a page steadily never reaches. What a page sends by itself, with nobody at it, reopens a conversation three times and then once for every five minutes, so that a page that sends on a timer cannot keep an agent running. All the conversations of one machine together are reopened thirty times at once and then once for every ten seconds. Nothing is lost past these: the clicks wait, and go together with the next reopening. A person's click is never held up behind what a page sent by itself.

**You can stop it.** While a conversation that It reopened is running, the bar above its page says "Working", with a Stop button beside it. The agent is asked to end, and ended a few seconds later if it has not, and so is any command it was in the middle of. Where its machine is out of reach, the bar says that it was asked to stop and that the machine is told when it is back. What it had been asked stays in the conversation, as it does when you stop a turn in the app. What was still waiting for that conversation on that machine goes with the stop (a conversation of the same name on another of your machines is another conversation, and keeps what waits for it): it is not reopened for, it is not handed over when you next open the conversation, and it no longer counts as waiting. The next thing you do on the page reopens the conversation as before, and the agent is told then that its last turn was stopped. Any browser that can use the page can stop it. A machine cannot, so no agent stops another. Stopping It's service ends the conversations it reopened as well, and what they were reopened for is given back and reopened for again when It next starts. The same holds when the service dies or the machine is started again in the middle of a run: when It next starts it ends whatever is left of the run, and the conversation is told, with what it is next reopened for, that an earlier turn was cut off and may have done part of its work. A run that It cannot note down as it starts is ended before it is given anything to do. Where It cannot tell whether an earlier run is over (it could not look at what was running, or could not read its own note of it), it holds the conversation back, or all of them where the note itself could not be read. A conversation held because its run could not be looked at is reopened again once the machine has been started again. `it runs` on that machine says what is held and why, and `it runs clear` lets them be reopened sooner, once you have looked that no agent It started is still running there. Where the note itself could not be read, only `it runs clear` lets them be reopened again, also after the machine has been started again. What was waiting for a conversation while it was held is tried again when it no longer is.

**Where it cannot be done, the page says so.** "Couldn’t wake" and the app's name, with the reason beside it: the app was not found, its command ended with an error, the folder the conversation was held in is gone. Where the app's command ended with an error, the last line it printed is on the page too, since that is often the only word of why; it is shown on the page and is not written into It's log. While the app runs, everything it prints is kept in a file of yours alone in `~/.it/logs`, which is how that last line is read. The file is removed when the run ends, and the next time It starts if It was ended first. It tries four times in all, further apart each time, and then leaves the click waiting, to be handed over the next time the conversation runs. It knows which folder a conversation was held in from a note kept in `~/.it`: the `it` command writes it each time the conversation publishes a page, and Codex's add-on says it with every turn, since Codex runs the agent's own commands where that folder cannot be written. The note leaves the machine no more than anything else there does.

A conversation that is open in a window where It's add-on is not loaded looks closed to It. For Claude Code, one that wrote something in the last twenty seconds is left alone until it is quiet. For Codex on Linux and macOS, It asks Codex's own record of which conversations are being written: one that a Codex has open anywhere on the machine (the terminal, the desktop app, an editor, T3 Code) is never reopened beside it, and Codex goes on holding a conversation for about a minute after its window is closed. A Windows lock file alone proves neither that its conversation is open nor that it has closed after a crash. It leaves that liveness unknown and queues nothing on that evidence. Open the conversation to receive clicks through its hooks or use `it wait`. Windows Auto-wake remains unavailable.

### Codex

While a turn runs, the click is handed to the model at the next tool call, and the turn goes on with any click that arrived after the last one. When the conversation is open and idle, the click goes into Codex's own queue, which starts a turn with it. What stands in the conversation for it is the mark `[It]` and nothing else. The agent is handed what the mark stands for by the add-on's hook that Codex runs as a turn begins, beside the message and not as a part of the conversation you read. Where the conversation's hooks have not been heard from, so that It cannot tell that they run there, it is one short line instead, as in Claude Code: the page, what was done, and the action's id. Nothing an action carried is in that line, and nothing you typed above a page either, since it is given to Codex's command as an argument, which other users of the machine can read. Codex reads the rest with `it action`. What a mark stands for is kept across connector restarts until a hook has said that the agent has it, so an answer that is lost on the way is asked for again. Where no hook says so within twenty seconds, the short line is sent after the mark, and that conversation is given the short line from then on. Should the app not take the line either, it is tried again three times over six minutes, and what the mark stood for stays with the connector for the next of the conversation's hooks that runs. The attempt count and the next retry time survive a connector restart. A restart does not grant more retries after the last attempt. A click that arrives in the middle of a turn is said to be a separate one, so that a second press of a button is not taken for the first.

Codex runs an agent's commands in a sandbox, and as it comes that sandbox reaches nothing on your machine: not a port, and not a socket in a folder. `it` has to reach It, so in the sandbox it is stopped, and it says so: its answer has the code `blocked`, and says that It could not be asked from there. There are three ways to live with that. It changes nothing in Codex's settings itself, whichever you choose.

**Let `it`, and only `it`, out of the sandbox.** Codex reads rules from every file ending in `.rules` in `~/.codex/rules`, or in the `rules` folder of wherever `CODEX_HOME` says it keeps its settings, and that is the folder It names when it tells you of this. Make one there, `it.rules`, with this one line in it, and start Codex again:

```
prefix_rule(pattern=["it"], decision="allow")
```

Every `it` command then runs without Codex asking, and the sandbox is as it was for everything else: another command is still kept from the network and from writing outside its folder. `it setup` and `it status` tell you of this rule when neither it nor a sandbox with the network is there, and the answer a sandboxed agent gets carries it for the agent to pass on. What the rule means is that `it` runs unconfined, so an agent can do through `it` what `it` can do: publish a file it names as a page, and save a file that a page sent into a file it names.

**Approve `it` each time.** In a git folder Codex asks before it runs each `it` command outside the sandbox. Its "don't ask again" covers the command with the words that follow it, an action's id among them, so it asks again for the next. In a folder that is not a git repository, Codex as it comes refuses the asking itself: nothing can be approved until you choose "Ask for approval" under `/permissions` in that conversation.

**Give the sandbox the network.** `it` then reaches It from inside the sandbox, and so does every other command the agent runs. In Codex 0.160 that is a permissions profile of your own with the network enabled, chosen in the first line of Codex's `config.toml`:

```toml
default_permissions = "workspace-network"

# The rest of your settings stay as they are, and these go at the end:

[permissions.workspace-network]
extends = ":workspace"

[permissions.workspace-network.network]
enabled = true
```

The first line has to stand above every table, which is every line in square brackets, or Codex will not start. The older setting, `network_access = true` under `[sandbox_workspace_write]`, does this only together with `sandbox_mode = "workspace-write"`: by itself it gives a git folder the network and leaves any other folder read-only.

None of the three is needed where Codex runs with full access. An app that runs Codex for you chooses the sandbox itself, whatever these files say: T3 Code gives Codex a sandbox of its own for each of its modes, and its default is full access.

Codex runs none of the add-on's hooks until you have approved them, and says nothing when it skips one. In the terminal, Codex asks the next time it starts, and "Trust all and continue" approves them. Until then a click still arrives, as a new message when Codex is idle. `it setup` and the site say that the hooks are waiting to be approved until one of them has run. How the desktop app and T3 Code ask, where there is no terminal to show the question, is not known.

The same add-on serves Codex in three places, and they differ in what happens to a click:

- **In the terminal.** A click reaches a busy conversation and an idle one.
- **In the desktop app.** A click for an idle thread starts a turn by itself. A click for a busy thread waits in view there, with a Steer button, and runs by itself when the turn ends. Delivery in the middle of a turn is not proven in the desktop app.
- **Inside T3 Code.** A click in the middle of a turn reaches that turn, as in the terminal. A click for a thread that is not in the middle of one is put to the thread in T3 Code, which starts a turn there, whether T3 Code still holds its Codex session or has closed it, as it does after 30 idle minutes and when T3 Code itself is started again: [T3 Code](#t3-code) says how.

### T3 Code

It has no add-on for T3 Code. T3 Code runs the unmodified Claude Code and Codex, so their add-ons load inside its sessions. Claude Code's add-on is alive for as long as T3 Code holds the program it runs for a thread, and a click on an idle thread starts a turn through it, which T3 Code shows. Codex's add-on runs only at moments inside a turn, so it hands over a click that comes in the middle of one and can do nothing for a thread that is idle.

T3 Code shows the turns it starts itself. A turn that Codex's own queue starts, inside the very Codex that T3 Code holds for a thread, runs and changes the page, and the thread shows nothing of it. And T3 Code lets a thread's program go when the thread has been quiet for a while, and when T3 Code itself is started again: the add-on goes with it, and the conversation is then closed as far as its agent app can tell, while the thread is where you left it. So a click for a conversation in a thread that its add-on is not there to take is put to the thread: T3 Code starts a turn there, in the mode the thread is held in, and you see it in the thread as you would a message of your own. It is the mark `[It]` and nothing else, for Codex and for Claude Code: a turn cannot be started with no message at all, and the agent is handed what the mark stands for by its add-on as the turn begins, where the thread does not show it. Where It cannot tell that the conversation's add-on runs, or the thread is in the middle of a turn, it is one short line instead: the page, what was done or what you typed above it, and the action's id. None of what It says to an agent about a click is put into the thread either way. Where the thread is in the middle of a turn, T3 Code keeps the click for when that turn is over. This is not Auto-wake, and does not ask whether Auto-wake is on: nothing is run that T3 Code does not show.

For this It asks four things of the T3 Code server on the same machine, and nothing of any other: a session of its own, which T3 Code's own command issues (`t3 auth session issue`, for reading threads and sending to them, kept in memory and never written down); which thread holds the conversation, which T3 Code knows by the id the agent app gave it; which conversation a thread runs now and which it ran before, as a Claude Code or Codex conversation is heard from; and that the click be put to that thread. It does this wherever T3 Code is running, and there is nothing to set up. In T3 Code's list of sessions it is the one labelled "It". All four are asked of the server itself, whatever proxy `HTTP_PROXY` or a variable like it names where It runs, so neither the session nor a click's words are handed to a proxy.

Where T3 Code is running, the first click for a Codex conversation waits for T3 Code to say whether it has a thread of it, which took between a fifth of a second and two seconds where it was measured, and what it said is kept. T3 Code is given five seconds to say. Past that the click is not kept waiting for it and goes the way it would without T3 Code, and what T3 Code says in the end holds for the clicks that come after. Where T3 Code is not running, or does not take the click, the click goes the way it would without T3 Code: into Codex's queue where some Codex has the conversation open, and otherwise the conversation is reopened as any closed one is, if Auto-wake is on for its agent app. Either way that turn runs where T3 Code does not show it.

The search starts with the likeliest active threads and reads at most 96 thread snapshots, in passes of up to 24, using one listing. Failed reads count towards that limit and stay retryable while the search has room. It remembers that a conversation has no thread only after every listed active candidate has been read successfully. Archived and deleted threads are excluded.

A search that reaches the limit stops without deciding that the conversation has no thread. Another search can begin six hours later. A matching thread beyond the limit can still be missed, and the click then goes through the same fallback routes as when T3 Code is unavailable.

T3 Code lets you switch a thread to another agent app, from Claude Code to Codex or back. The thread then runs another conversation, under the id the other app gives it, and lets go of the one it ran before. The pages the earlier conversation made go with the thread. When It hears from a conversation that T3 Code says a thread runs now, each conversation the thread ran before carries on as this one: every page of theirs on this machine becomes this conversation's, under any id the earlier one had, with the clicks that wait on it and the words of a mark that was put into the thread for it. The page then names the app the thread runs now, the agent there changes it as its own, and `it wait` there waits for its clicks. Pages on another machine stay where they are. Only the thread's own conversations are handed over, by what T3 Code says of that thread, and never one of another thread, however alike their folders. A conversation that a helper runs for one of the thread's turns is the helper's, and is not handed over either. A conversation that is listening or in the middle of a turn at that moment is in use, and keeps its pages until it is quiet.

It asks this at most once a minute for a conversation that a thread runs. For one that it finds in no thread, it asks again a few times in the first minute, since T3 Code may not yet have the new conversation's id from its app, and then every ten minutes. It reads only the threads that are in the middle of a run or changed in the last ten minutes, at most eight of them, and only the thread it already knows of where it knows one. Where T3 Code is not running nothing is asked, and pages that changed hands stay where they went. A switch is seen only between Claude Code and Codex, and only once the new conversation's add-on has been heard from: in Codex, once its hooks have been approved. What T3 Code says of a thread names the conversations of about its last ten turns, so a conversation that the thread let go of more than ten turns before It heard from the new one keeps its pages. Following a switch has been tried against a stand-in for what T3 Code answers, and not yet in a real T3 Code thread.

T3 Code shows Claude's reply to a click that the add-on handed over, and not the click's text; a click that was put to the thread is shown as the message it is. Delivery in the middle of a turn is not proven inside a T3 Code thread, for Claude Code or for Codex.

### Pi

A click arrives as a message from you. When Pi is idle the message starts a turn. When Pi is working, Pi reads it once the tools it is running have finished and before it next asks the model, so that nothing is interrupted.

### OpenCode

After opening a saved conversation, send one message in it to start listening. OpenCode's supported plugin events do not identify a selected saved conversation before a turn. It does not choose the newest session or substitute the default agent. While that loaded app reports this discovery limit, Auto-wake waits for its closed conversations too, to avoid opening a second copy of an idle one.

A click starts a turn when the conversation is idle, and joins the running turn at its next step otherwise. One OpenCode holds many conversations, and a click goes to the conversation that made the page, whichever one is on screen.

### Hermes Agent

After opening or switching to a saved conversation, send one message in it to start listening. Hermes's session-start hook runs on a first turn, not on selecting a saved idle session. The add-on reports that limit without guessing the selected conversation. While the loaded app is heard from, Auto-wake waits for its closed conversations too, to avoid opening a second copy of an idle one.

Where a click can arrive depends on where Hermes runs:

- **In the plain `hermes` terminal**, a click starts a turn when the conversation is idle. While a turn runs the click waits, because a message sent then would interrupt the turn.
- **In the TUI and the desktop app**, a click arrives only in a Hermes later than 0.21.5, and only once you have allowed it, which `it setup` says how to do. Hermes itself then keeps the click until the running turn is over. In Hermes 0.21.5 and earlier, a click for these waits in the inbox.
- **In the messaging gateway**, a page made after an agent's first turn has no conversation to send clicks to. Those clicks wait for `it wait` or the site.

One narrow window is known and accepted: in the terminal a click is handed over only when nothing you typed is waiting, but a `/resume` entered in the instant between that look and the hand-over takes the click with it into the other conversation.

In the TUI, desktop app and gateway, the add-on checks Hermes's permissions after asking the connector. It then checks that the chat still holds the same conversation. If a hook has reported another conversation there, the click stays with the original one. Hermes accepts a message by the chat's name, without an expected conversation id. A switch after that final check can still send the click to the replacement conversation.

### OpenClaw

The add-on runs inside the OpenClaw gateway and puts a click into the conversation that owns the page. What happens next is OpenClaw's own doing, as for any message:

- **The conversation is idle.** A turn starts with the click.
- **A turn that a click began is running.** OpenClaw puts the new click into that turn, and the agent reads it at its next step.
- **A turn that something else began is running**, such as one you started from OpenClaw's own interface. The click waits in line behind it, and starts a turn when that one ends.

A gateway is always there, so there is no Auto-wake for OpenClaw and nothing to reopen. While the gateway is stopped a click waits, and it arrives by itself once the gateway is running again, a little after it has started. A conversation is asked about for a month after the last command its agent ran, so a page left up for a week is still answered. One gateway is asked about at most 40 conversations at a time, the ones that ran a command most recently.

It is connected to one OpenClaw profile at a time. OpenClaw gives a conversation the same name in every profile, such as `agent:main:main`, and the add-on asks for a conversation's clicks by that name. With the add-on in two profiles, what you do on a page made in one could be handed to a conversation in the other. So `it setup` refuses a second profile, which to It is an OpenClaw that `OPENCLAW_HOME`, `OPENCLAW_STATE_DIR` or `OPENCLAW_CONFIG_PATH` points somewhere else, and says how to move the add-on there: untick OpenClaw in `it setup`, which takes the add-on out, and run `it setup` again where OpenClaw is pointed at the profile you want. Where an earlier It put the add-on into two profiles, the next `it setup` or the background service within half an hour tries to take it out of all but the one it was put into last. Until that removal is confirmed, setup and the machine's inventory report an error and say that a second profile may still receive and answer clicks, including on new pages. The service logs that warning and retries each half hour, and every `it setup` retries as well. Reporting the error does not suspend delivery: the other profile's add-on can still receive the full wording of clicks from new pages, send them to its own conversation and acknowledge them. Once removal succeeds, a page made from a profile it was taken out of may still be answered in the one that is left, where that has a conversation of the same name. A profile that is chosen in some way other than those three variables is not told apart at all. Two recorded paths that OpenClaw reports as the same real add-on folder count as one installation, and the extra record is retired without removing the add-on. If those folders cannot be resolved or OpenClaw cannot say where its add-ons are, nothing is removed, and setup and the background service retry later.

A helper that the agent starts, and a run on a schedule, are given no conversation: a page one of them makes belongs to nobody, and its clicks wait in the inbox. OpenClaw names their sessions `agent:<agent>:subagent:<id>` and `agent:<agent>:cron:<job>:run:<run>`, which is how the add-on knows them.

**It is held back.** `it setup` does not offer it, and installs it only for someone who asks for it by name: run `IT_EXPERIMENTAL=openclaw it setup` once. That it was asked for is then written down in It's folder, so the background service, and the `it` that OpenClaw's agent runs, keep it without the variable. `it setup --only openclaw` in a folder where nobody has asked is refused, and changes nothing. It has been run on a real gateway, OpenClaw 2026.9.6 on Linux with a real model, for a conversation held in OpenClaw's own interface: a click when the conversation was idle, when it was busy in each of the two ways above, three clicks at once, a click straight after the gateway restarted, and a click made while the gateway was stopped. It has not been run for a conversation held in a chat channel, such as Telegram or WhatsApp, which is where most OpenClaw conversations are. There the agent's answer to a click is meant to go to the chat, as its other answers do, and these things are not known:

- Whether that answer goes to the chat it should, and to nowhere else.
- Whether a click leaves the conversation's record of where it was last reached as it was. In OpenClaw's own interface, where a conversation has no such address, the record afterwards named It as the last channel.
- Whether a click is held to the restrictions OpenClaw applies to that conversation's own messages. A turn a click began was offered fewer of the agent's tools than a turn begun from OpenClaw's own interface, 44 against 57 in the run above, and which were left out was not looked at.

## What It does not do

- A conversation is reopened when it has been closed only on a machine where Auto-wake is on for its agent app. Where you have turned it off, a click for a closed conversation waits in the inbox.
- It does not use ACP, which cannot reach a conversation another program owns: the conversation It has to reach is the one you already have open.
- It ships no MCP server, so it has no add-on for an agent app that could be reached only through one, such as Crush.
- It builds no add-on on an agent app's undocumented API, or on an interface for add-ons that is not stable, which is why it has none for Copilot CLI. The Hermes add-on is the one that reaches past that line: besides Hermes's interface for plugins it reads a few of Hermes's own fields, to tell whether a turn is running and where to put a message, and a Hermes that changes them can leave clicks waiting. Codex's is told whether a conversation is open by the lock files Codex keeps, which are Codex's own too.
- It uses no queue but Codex's. Qwen has a queue of the same kind, and It has no add-on for Qwen.

Any agent app without an add-on still gets the `it` command, the agent skill (`addons/skill/SKILL.md`, which `it skill` prints), `it wait` where the app can wake on a command's output, and the inbox. No click arrives there by itself.
