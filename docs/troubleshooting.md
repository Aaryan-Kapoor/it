# When something does not work

Start with `it status`. It says how things stand on this machine in a few sentences, and where something is wrong it says that first, with what to do about it. This page is for what it sends you to, and for the things it cannot see from where it runs.

## Where the log is

The background service writes down what happens in `~/.it/logs/it.log`, which only your user can read, and `it service logs` prints the end of it. The file is kept to its newest few megabytes. A line there names what happened and carries ids, counts and fixed codes. It never carries what was on a page, a name you typed, or a file's path.

Where the service could not start, the log has one line, `could not start: <code>`, and the table below says what each code means. The explanation in full sentences can name folders on your machine, so it is said only to a person at a terminal: run `it serve` there to read it. Where fixed words say what to do and running the service again would not help, those words are said wherever `it serve` was run, with no terminal as well, and they name no folder or process. That is the case where It has not been set up, which says to run `it setup`, where It is already running or its lock could not be taken, and where the command runs as an account that may not read It's folder.

`it service status` says whether It is running, whether it is registered to start by itself, and whether it is ready to hand what is done on a page to the conversations on this machine.

If a background start fails, It waits 30 seconds, then two minutes, then ten minutes between attempts. If the machine stays offline, a request times out or another temporary failure continues, It keeps trying every ten minutes. A failure that requires repaired settings or data, or a replacement backend program, stops automatic attempts immediately. An unreadable `startup.json` is moved aside as `startup.json.unreadable`, reported once and its retry count forgotten; it does not prevent a start. `it service status` shows the last code and whether a retry is waiting or stopped. Run `it serve` in a terminal to read the full explanation, or, where It was never set up, run `it setup`. After fixing the cause, run `it service install` to retry in the background. That command clears the retry count. Changed startup settings or a newer It get a fresh attempt the next time the service starts. Once It starts successfully, a later crash restarts normally.

## What the service could not start for

The code is one of these, or the system's own code for what a file or a socket refused, such as `EACCES`.

| Code | What it met | What to do |
|---|---|---|
| `invalid` | `IT_PORT` is set, and names no port It can use. The port has to be a whole number with 41 more ports above it, which is where the backend program's two are. And neither it nor the port above it, where the pages are, may be one that no browser opens a page on: browsers keep a list of such ports, 6000 among them, and It would run there and never be opened | Set `IT_PORT` to such a port, or unset it |
| `not_set_up`, `settings` | It has not been set up in this folder. Its settings file, `service.json`, is not as It wrote it | Run `it setup`. Where the settings are not as It wrote them, put the file back as it was: it holds the keys to what It keeps, and It makes no new ones in their place |
| `record_unread` | A record that It keeps beside its database and goes by is there, and is not as It wrote it: what it notes of the database, in `backend/data.json`, or what it keeps of the erasings it was told of, in `backend/erased.json`. Such a record is never taken for one that says nothing, so nothing is started. The same code is what a setup or a joining says of this machine's identity, or of the keys it waits to be enrolled with, and what an erasing stops with where a folder named as a copy does not say which copy it is. | It names the file, and says what you can do about that one: put it back as it was, or move it away where that is safe |
| `home_unfit` | It's folder is on a disk that did not let It make a file in the one way that only one program at a time can, which is how its settings and its locks are made | Keep the folder on a disk of the computer's own, and not on a memory stick or a network share. `IT_HOME` names another folder |
| `already_running`, `lock_not_taken` | Another service holds the folder. The lock could not be taken, because another program keeps putting one in its place | It is running already: `it service status` says so. Stop the other one first if you meant to start this one |
| `cannot_list_processes` | The system's list of running programs could not be read, or one of your own programs is running and the system would not say what it was started with. Either way It cannot tell whether a backend program was left on its folder, and starts none | It reads the list with `ps`, or on Windows through PowerShell, which has to be allowed to run. Something that confines It, such as a sandbox it was started in, may keep it from that. Where a program is named, and it is a backend program, end it |
| `still_running` | A backend program left on the folder by a service that is gone is still there: it did not stop when asked, or more of them go on being started. Or something may be such a program and the system does not show it to be the backend program, so it is not asked to stop. Or a backend program that runs in another folder has this folder's database, which has a second name there: it is that folder's to stop, and is asked nothing. Or a program runs under the name this folder's settings give its backend, and nothing the system shows says that it runs on this folder's database: it may run for a copy of the folder, or have been left on this one before the folder was given another name, so it is asked nothing. Or a process has the number the folder's backend program had and cannot be told to be that program, or a backend answers for the folder and nothing says which process it is. No second one is started on the same data | It names the process by its number. Where it is a backend program left on this folder, named `convex-local-backend`, end it with an interrupt, as Ctrl-C at a terminal would, and start It again. Where it runs for another folder or for a copy of this one, stop It there |
| `offline`, `checksum`, `unsupported`, `backend_program` | The backend program could not be fetched. What was fetched is not the file It expects. None is published for this system. It could not be unpacked or started, or `IT_BACKEND_BIN` names no file | Check that the machine is online, or that the place `IT_BACKEND_RELEASES` names holds the release, and try again. The whole of it has twenty minutes to come. On a connection that is working and too slow for that, give it longer: `IT_BACKEND_FETCH_MINUTES=90 it setup`. A second `checksum` means that something between this machine and the release is changing what is fetched |
| `backend_releases` | `IT_BACKEND_RELEASES` is set, and does not name a place the backend program may be fetched from: an https address, or this machine itself over plain http, as `127.0.0.1` or `localhost` with its port. Nothing is asked of what it names, and what it holds is not said back | Set it to such an address, or unset it to fetch from the program's own releases |
| `backend_older` | The data has the functions of a newer It than this one in it, or a newer It began to load its functions into it and how that ended was never learned, or a newer backend program than this version of It runs has run on it, or one that cannot be told to be older. An older one is not started on it | Install the version it names, or a newer one. As a last resort, put back the copy of the database from before the newer one changed it, as [Going back to an older It](data.md#going-back-to-an-older-it) describes, which loses everything done since the upgrade |
| `copy_failed` | No copy of the database could be kept before a newer backend program was started on it, or before other functions were loaded where none that were loaded before answer: for want of room, or because something It did not make has the copy's name, which It leaves as it is | Make room on the disk for a second copy of the database, or move what has the copy's name somewhere else, and start It again |
| `port_in_use`, `port_taken`, `cannot_listen` | Another program has one of the backend program's two ports. Another has the site's port or the pages'. The door could not listen for another reason | Stop whatever is using the port, or give It another port to count from with `IT_PORT`. [A port another program has](#a-port-another-program-has) says which ports those are |
| `database_unfinished`, `database_unopened` | The backend program could not open the database. It was begun and never finished, with nothing ever loaded into it. Or it will not open for another reason. Either way nothing there is moved or removed | Where the database was never finished and It was never used on this machine, move the folder `~/.it/backend` out of the way and run `it setup` again. Anything else is said with what the backend program said of it |
| `backend_exited`, `backend_silent` | The backend program ended as soon as it was started, and what is in the folder is left as it is. It was started and did not answer, or stopped answering while the functions were being loaded | Run `it serve` in a terminal, which says what the program said as it ended, and start It again |
| `functions_refused`, `settings_refused` | The backend would not take It's functions, and none that were loaded before answer. It would not take their settings | Run `it serve` in a terminal to read why. Nothing in the database was changed |
| `port_changed` | The functions of this version could not be loaded, and the ones in the database were loaded for another port than the one It was given | Put the port back with `IT_PORT`: it names the port |
| `error` | Anything else: what stopped the start has no code of It's own and none of the system's | Run `it serve` in a terminal, which says what it was |

## What the door refused

The door is the one part of It that a browser, another screen or a machine on another computer reaches. Where it refuses a request it writes `door refused a request (<code>)` in the log, once every ten minutes for each code, with how many more like it there were since. The line says nothing of what was asked or of who asked. Most of these need nothing done: the door did what it is there for.

| Code | What it means | What to do |
|---|---|---|
| `unknown_host` | Something asked It by a name that is not this machine's, or from an address It does not answer: with the network on, one that is not a private network's, and kept to the tailnet, one that is not the tailnet's | Open It by one of the addresses `it network` lists, from a device on the same network or your tailnet. Where it was not you, a page of another website tried to reach It through a browser by a name pointed at your machine, or a device on the internet tried to reach It, and was refused |
| `too_many_wrong_codes` | A pairing code came from an address that has had ten refused in the last minute | Wait a minute, and use a code made just now. Where it was not you, someone on the network is trying codes: a code is too long to come upon so, and `it network off` shuts the network out |
| `foreign_origin` | A page of another website asked for one of It's routes through a browser | Nothing. It was refused |
| `method`, `bad_request`, `no_such_thing`, `api_path`, `session_method`, `upload_method`, `download_method`, `control_method`, `call_method`, `call_type`, `call_as` | Something asked the door for an address it does not have, or in a way that It's own site and command never do | Nothing, where the site and the `it` command work: it was another program, or something looking at what answers on the port. Where a command on a machine that joined is refused so, that machine and this one may run different versions of It: `it version` says which each is, and the older is the one to update |
| `websocket_path`, `not_a_handshake`, `handshake_body`, `handshake_early`, `websocket_version`, `websocket_key` | Something asked for the live connection that the site keeps with It, at another address than the site does or not in the way a browser asks for one | Nothing, where the site stays current in your browsers: It's own site does not ask so |
| `too_large`, `too_slow`, `length_required`, `headers_too_large` | A request was longer than It takes, did not arrive in time, did not say how long it was, or had more than 16 KB of headers | Where a publish failed, the `it` command said which limit it met, and [How much It takes](data.md#how-much-it-takes) lists them. On a slow network, try again |
| `backend_unreachable`, `backend_no_websocket`, `backend_slow` | The backend program did not answer the door, did not agree to a live connection, or was not taking what a browser sent | Once is nothing: the site asks again. Where it goes on, `it status` says whether It is running, and the lines that begin `backend:` in the log say what became of the backend program |
| `not_local`, `push_not_local`, `push_no_such_thing`, `push_token`, `push_for_another_route`, `push_body_not_the_one_signed` | Something other than It's own backend asked the door to send a notification, or to pass a message on inside It | Nothing. Only It's own backend, on this machine, may ask either, and the request was refused |
| `push_malformed`, `push_not_a_push_service`, `push_too_long`, `push_subscription` | A notification could not be sent to a browser whose site is closed, because what there was to send it with was not as it should be: the request itself, the address of the browser's push service, the length of the text, or the keys the browser gave | Nothing, where notifications arrive. The notification is still shown on every screen that has the site open |
| `push_backend_keys`, `push_service_unreachable` | A notification could not be sent to a browser whose site is closed: the keys to check the request with could not be read, or the browser's push service did not answer | Check that the machine is online. The notification is still shown on every screen that has the site open |
| `accept_failed` | The system could not hand the door a connection | Once is nothing. Where it goes on, stop It and start it again |
| `content_failed`, `fault` | Something went wrong inside It while it answered | Where it goes on, report it, with the lines around it in the log: they hold ids and codes, and nothing that was on a page |

## A port another program has

It counts every port from one, which is 4700 unless `IT_PORT` names another: the site is on that port, the pages are on the one after it, and the backend program has the two that are 40 and 41 above it, 4740 and 4741. Where another program has one of them, It does not start, and says which port it was.

The other way about, a program that is not It may answer at the port where It's site would be. `it status` then says that It is not running on this machine and that another program answers at that port, and on a machine that joined, that what answers at the address is not the It it joined.

A first setup looks at the four ports before it fetches or writes anything. Where one of them is taken, by a program or by another It (another person's on the same machine, or one set up in another folder), it sets nothing up, says which, and names a first port that is free: `IT_PORT=4800 it setup`, say. The port is written into the settings of that It, so it is named that once.

Either stop the other program, or give It another port to count from. The first run writes the port into `~/.it/service.json`, and wherever `IT_PORT` is set afterwards it is used in place of the one written there, so set it where It is started. For the background service that means setting it and running `it service install` again, which registers the service with it.

Another port is another address for the site. A browser that was paired stays paired, and is taken for a new display. A machine that joined from another computer keeps the address it joined by, and has to be told the new one, as [Agents on another computer](agents.md#agents-on-another-computer) says.

`it network on` fails with `cannot_listen` where another program has one of It's ports on the machine's network addresses. The network is left off, and It goes on answering the machine it runs on.

## An agent that says It is not there

An agent app that runs commands in a sandbox may give them no network. `it` then cannot reach It, though It is running, and answers with the code `blocked`: "It could not be asked from here". `it status`, asked from there, says `"blocked": true` and gives `running` as not known, since it cannot see. Let the agent run `it` outside the sandbox, or let commands in the sandbox use the network. For Codex, `it setup` writes a rule that lets `it` out and leaves the sandbox as it is for everything else, and Codex reads it when it next starts, so a Codex that was already running during setup has to be started again. If `it` is still stopped after that, a file named `it.rules` that It did not write may be in its place, and [Add-ons](add-ons.md#codex) says what to put in it. On Windows, Codex's elevated sandbox runs commands as accounts of its own, which It's folder is kept from: there `it` says that it may not read It's folder, the network does not help, and the rule is the way. Nothing else needs starting again.

## Codex asks before every `it` command

After an agent has installed It from inside a Codex conversation, or `it setup` has connected Codex while a Codex was open, that Codex asks you to approve each `it` command the agent runs, unless it runs with full access, and what you do on a page reaches it only once it is idle. Nothing is broken. Codex reads the rule that lets `it` out of its sandbox, and asks to review It's hooks, only as it starts, and this Codex started before setup wrote either. Quit Codex and start it again, and choose "Trust all and continue" when it says the hooks need review. In a terminal, `codex resume --last` brings the conversation back. From then on `it` runs without asking. Two kinds of command go on asking, as they are meant to: `it save`, which writes a file a page sent, and the commands that can change It on the machine, such as `it setup` and `it upgrade`.

In a thread of T3 Code there is nothing to approve: Codex never asks about It's hooks there, and what you do on a page reaches the thread through T3 Code. If a Codex that has been started again still asks before every `it` command, it is not reading It's rule: `it status` says when no rule lets `it` out, and [Add-ons](add-ons.md#codex) has the rule, where Codex reads it from, and what a file named `it.rules` that It did not write means.

## A pairing address that does not work

A code pairs one browser, once, and works for ten minutes. An address from `it site`, or one made on the Displays page, is refused once its code has been used or its ten minutes are over, and the way on is a new one: run `it site` again, or choose "Add a display" again.

- **Too many wrong codes.** The door lets one address try ten wrong codes a minute. After that it refuses every code from that address until the minute is over, a right one included, so wait a minute and use a code made just now.
- **A screen that was paired asks to be paired again.** A browser keeps its pairing for the name or the address it opened the machine by. A screen paired at `http://192.168.1.20:4700` is not paired at the machine's host name or at another of its addresses, so open It by the address the screen was paired at. If the router has given the machine another address, pair the screen again, and give the machine a fixed address on the router to keep that from happening.
- **A phone on shared Wi-Fi cannot open the address at all.** Many venues', hotels' and offices' Wi-Fi keeps the devices on it from reaching each other, so a phone there cannot open the machine's address, and nothing says why. Use your tailnet instead: install Tailscale on the phone, sign in with the same account as the machine It runs on, run `it network tailscale` there, and open the address it gives. [Phones and shared Wi-Fi](screens.md#phones-and-shared-wi-fi) says more.
- **Another screen cannot open the address at all.** `it network` says whether the network is on and at which addresses other devices open the site. A firewall on the machine has to let the site's port and the pages' port through, 4700 and 4701 unless you chose others. An address that says `localhost` is for the machine It runs on, and no other device can open it. To have the links agents give at an address another device can open, choose one under Displays, in "Links agents give".
- **"It does not answer to this name."** It answers to the machine's own names and addresses and to nothing else. Open it by one of the addresses `it network` lists.

## A page that cannot use the microphone or the camera

A page hears the microphone and sees the camera only through It, and It tells the page why where it does not, which a page should show:

- **"This screen reaches It over plain http."** A browser gives a site the microphone and the camera only at `localhost` on the machine It runs on, or at an `https` address. Run `it https on` on that machine, and open It at the address it prints. [Screens](screens.md#over-https-on-your-tailnet) says how.
- **"The person did not allow this page to use the microphone on this screen."** Someone pressed "Not now" in It's bar. It asks again the next time the page is opened.
- **"It uses the microphone and the camera for a page only while this screen shows it."** The page asked from a tab that was not shown, or a window that was minimized. It works again once the page is in front.
- **"It asks the person only while the page is in front, in the window they are using."** The page asked to be allowed from a window that was shown but not the one in use. Ask again from something the person does on the page.
- **"The screen stopped showing the page, so It closed the camera, and took no photo."** The tab or the window was put behind while a photo was being taken.
- **"The browser did not let It use that on this screen."** The browser itself was told no for It's site. Allow the microphone or the camera for that address in the browser's site settings, and try again.
- **"The microphone or the camera is in use by something else on this screen."** Another app, or another tab, has it. Close that and try again.
- **"It.microphone was not called from a click or a key in the page."** A browser starts sound for a page only once someone has clicked or typed in it, so a page that opens the microphone, or the camera with sound, by itself is refused. Press the page's own button for it.
- **"The browser did not start the sound for It on this screen."** The browser held It's own sound back. Click once anywhere on It and press the page's button again.
- **"This browser cannot pass the microphone's sound on to a page."** The browser lacks what It gathers the sound with. A current Chrome, Edge, Firefox or Safari has it.
- **"It does not record for a page."** The page asked It to record for it, which It does not do. Ask its agent to publish it again: a page hears the microphone or sees the camera live, and records what it is given itself.

`it https on` can fail with `tailscale` where Tailscale would not serve: Tailscale is not running or signed in, MagicDNS or HTTPS Certificates are off for the tailnet in Tailscale's admin console, or on Linux your user may not change what it serves until `sudo tailscale set --operator=$USER` lets it. It fails with `port_taken` where Tailscale already serves something else on one of It's ports. `tailscale serve status` says what Tailscale serves.

## A page that does not arrive, or a click that does not

`it status` says whether each agent app is connected. Where It is running and is not handing what is done on a page to the conversations on this machine, it says so, and `it service logs` says what it met. A click on a page whose agent app is not connected waits where the site shows it, and the agent takes it with `it wait`. [Agents](agents.md) says which agent apps a click reaches by itself, and where it waits.

A display with the site open brings a page up when an agent asks it to. One whose browser is closed does not open by itself.

A Claude Code conversation that was already open when It's add-on was installed, such as the one in which an agent installed It, does not hear what is done on its pages: Claude Code loads an add-on as a conversation starts. Type `/reload-plugins` in that conversation, and from then on it does, and what was waiting for it is handed over. Until then Auto-wake does not reopen that conversation for a click on its pages, since the reopened copy would run beside the one you have open, and the page says to type `/reload-plugins` instead. `it setup` gives the agent the words to tell you when it connects Claude Code from inside such a conversation, and the agent is given them each time it publishes a page there. The site says it above the conversation's pages, and `it status` says how many open conversations have not loaded the add-on. A conversation that was open when It was updated is in the same place, and after an update from 0.1.36 it has no add-on loaded at all: type `/reload-plugins` in it as well. In a conversation of a Claude Code older than 2.1.287, start a new conversation instead.

After `it upgrade`, where you started It yourself with `it serve`, the It that runs is still the old version until you stop it and start it again. `it status` says so, with the two versions, until you have.

The bar above a page says what is still waiting, though something you did later is done with, and otherwise where the last thing you did has got to. What it says tells you what to do:

| The bar says | What it means | What to do |

| Saved on this browser, not sent yet | This browser has no connection to It for the moment | Nothing. It is sent when the connection is back |
| Can’t reach It | It has not answered for a few seconds: it is stopped, or this device has lost its network | Start It (`it status` on its machine says how it stands). What you did is kept and sent then |
| Sent. Waiting for your agent | It has it, and is handing it to the agent | Nothing, for the first seconds |
| Sent. … is busy, and gets it when it is free | The conversation is open and in the middle of something | Wait for its turn to end |
| Sent. … is not listening: its conversation looks closed | Nothing on that machine was listening for it: the conversation is closed, or its app is not running | Open the conversation again, or press "Wake it", where it is offered, to have It reopen it for this and from now on. It is offered in a browser paired as yours, for what was done in the last day, on a machine whose It reopens closed conversations, as It does on Linux, macOS and Windows. In Claude's desktop app, a conversation listens once the app runs it again, which it does when you send a message there |
| Sent. … is not connected on …, and gets it once it is connected there, under Machines | The agent app that made the page is switched off on that machine, under Machines. The machine hands nothing to such an app and reopens none of its conversations, whatever Auto-wake is set to | Connect the app again on the Machines page, or run `it wait` in its conversation to take this one thing. | Working | It reopened the conversation, and its agent is at work. "…more waiting" counts what else you did meanwhile, and "not sent yet" what has not left this browser | Nothing. Stop, beside it, ends the agent and drops what was waiting for it |

| Not sent yet. This browser could not save it, so keep this tab open | This browser would not store what you did, so it is only in this tab | Keep the tab open until it says it was sent |
| Couldn’t wake Claude Code: its conversation is open without It’s add-on, … | The conversation published this page while It's add-on was not running in it, as one does that was already open when the add-on was installed, and the add-on has not been heard from there since. Codex starts nothing from its own queue after that until you send a message there, so It has not put what you did into that queue | Send a message in that conversation. What you did is handed to the agent in the turn your message begins |
| Couldn’t wake Claude Code, with a reason and then "Its conversation has not loaded It’s add-on either" | It could not reopen the conversation, for the reason given, and the conversation published this page while It's add-on was not running in it, as in a conversation that was already open when the add-on was installed. This is said only where the reopening had begun before the page was published, since such a conversation is not reopened once It knows | Type `/reload-plugins` in that conversation if it is still open: what you did is handed over once the add-on there asks for it. | Couldn’t wake …, with a reason | It tried to reopen the conversation and could not: the reason follows, with the last line the agent app itself printed where it ended with an error | Put right what the reason names. What is still waiting goes on being said, and "Done" or a failure is said for ten minutes.

If a page says that a turn from before may still be running, or `it status` says that some conversations are not reopened for now, run `it runs` on that machine. It lists what It has reopened and what it holds back: a conversation whose earlier run it could not check on or end, or every conversation where it could not read its own note of what was running (kept as `runs.json.unreadable` in its folder). A conversation whose run could not be checked on is reopened again once It can verify that its processes are gone, which it looks for every minute, or once the machine has been started again. On Linux the usual cause is a process of yours that started while the run went on, that nobody can read (gpg-agent and ssh-agent are like that), and that It cannot show to be someone else's. It shows that most easily where It runs as the service `it setup` registers, since everything the service starts is then in a control group of its own. Started by hand with `it serve`, It shares a control group with whatever else runs in that terminal, and such a process started there in a session of its own, as gpg-agent is, holds the conversation for as long as it runs. You can also check that no agent It started is still running there and run `it runs clear`. Where it was the note that could not be read, starting the machine again does not put that right, so check and clear it in the same way.

A run is recorded before the agent gets work, so a full disk cannot erase that record. If the connector crashes, restarting It checks the run and any processes carrying its mark, ends those it finds, and releases the hold once it can verify that they are gone. On Windows the run was kept in a job of the system's, which ended with the connector: restarting It asks Windows whether that job is still there, ends it if it is, and releases the hold once Windows says it is gone. If the system cannot list or identify the processes, or on Windows cannot be asked about the job, the conversation stays held. It checks again before reopening it. An older uncertain record without a run mark cannot identify detached children, so that hold stays until you restart the machine or check that nothing from the run is still working and use `it runs clear`.

If the disk cannot save the notice that you pressed Stop, It keeps the run's record and the backend's Stop. It retries saving the notice while it runs. The conversation stays held until the notice is safe, and its next reopened turn is told not to continue the stopped work.

## An agent app after It is updated

`it status` names each agent app's add-on as the app has loaded it, and the Machines page does the same beside the app.

- **"outdated", or "Restart to update the add-on".** The app is running an earlier build of It's add-on than the one installed, as an app that was already running when It was updated is. Clicks still arrive. Restart the app, or T3 Code where the app runs inside it, to load the new build.
- **"incompatible", or "Add-on needs attention".** What the app has loaded cannot take clicks from this It: it speaks another delivery API than the connector, or the app lacks something the add-on needs. For OpenCode it can also mean that OpenCode refused to load the add-on, as OpenCode's own log says, so that nothing of It runs there at all. Clicks wait in the inbox, and the line beside the app says what to do. Where it says to update It and restart the app, run `it setup` and then restart the app. Where it says the app is missing a delivery API, update the app.

Where `it upgrade` said that an add-on could not be brought up to date, the app keeps the add-on it had, and It tries again each time it starts and every half hour. `it setup` tries again at once, and says why where it cannot.

## Claude Code on Windows that gets no clicks behind a proxy

On Windows, It's add-on inside Claude Code asks the connector at a port on the machine, and Claude Code sends what is asked of a port through any proxy its environment names. So where Claude Code was started with `HTTP_PROXY`, `HTTPS_PROXY` or `ALL_PROXY` set, in capitals or in small letters, the add-on asks nothing at all, so that the proxy is not shown which conversation is asked about, and clicks wait in the inbox. Nothing says so inside Claude Code. `it status` says so where its own environment is such an environment, as it is when an agent runs it inside that Claude Code, and its JSON has `"proxied": true` beside Claude Code.

Add `127.0.0.1` to `NO_PROXY`, and to `no_proxy` where that is set too, in the environment Claude Code is started with, and start Claude Code again. Naming `localhost` there is not enough. Claude's desktop app does this for its own sessions where it finds a proxy, and on Linux and macOS the add-on asks over a socket, which no proxy is given.

## Older backend functions

If an update cannot load its backend functions, It keeps serving with the functions already loaded. The site shows this beside its pages and on Machines. Some pages or controls may fail because the site and functions differ. In an owner browser, the warning points to `it status` on the machine It runs on for the reason. After resolving the reported problem, restart It to retry loading the functions. `it service logs` shows what the service met. A paired screen shows the warning and asks you to open your owner browser.

Machines compares the running versions already reported by the host and joined machines. A joined machine can say it is behind before its next release check. That alone does not offer an update: a release must also have been found by that machine.

## An update from the site that does not finish

The Machines page gives an update fifteen minutes from when you asked for it. Where the machine has not reported the new version by then, the page says the update did not finish and offers it again once the machine is on.

Where the page says that the new version is in place and has not been heard from since it was started, the program was replaced and the service stopped to start again as it, which is how an update from the site finishes on Windows. The launcher goes on starting the new program every five seconds, and the service's log on that machine says what it met: run `it service logs` there. When a start fails before It is ready, It waits longer between attempts, and for a failure that needs a change from you it stops trying and says why in the log. Once the problem is fixed, `it setup` starts it again. The program the update moved aside, `it.old.*.exe` beside `it.exe`, is removed when the new version starts, and otherwise by the next update.

On a Windows machine that joined an It, a background service that finds another It already running this machine's connector waits for it to stop, and says so in its log when it begins and then every half hour. It looks again after half a minute, and less often after that, down to once every five minutes. Once the other has stopped, the service ends and its launcher starts it again a few seconds later, so that it takes over as the program installed now and not as whatever program it was started as, which after an update is the one the update moved aside. The other may be an `it serve` you started in a terminal, or a launcher left running when its task was replaced.

## A warning about Tailscale Funnel

Tailscale Funnel opens a port of the machine to the whole internet, and It warns of one that forwards to It's ports on the network page, in `it network` and in `it status`, beside what they say of the network. [Network and privacy](network-and-privacy.md#tailscale-funnel) says which Funnels It sees.

- **"Tailscale Funnel makes It public, even with the network off."** A Funnel forwards from the internet to It, and It's network setting does not close it. `tailscale funnel status` lists each Funnel and where it forwards. Turn off the one on It's ports with the command for its kind, such as `tailscale funnel --https=443 off`, using the port the status names. It never changes a Funnel itself.
- **"It could not check Tailscale Funnel."** Tailscale is on the machine, and its command could not be run, did not answer within a moment, or said something It cannot read. Check that `tailscale funnel status` works for the user It runs as. Where Tailscale's command says its daemon is not running, and the system shows no daemon either, It takes that for no Funnel, and says nothing. Where the command says so and the daemon's socket or service is there, as when the system keeps the daemon's process from your user, It cannot tell, and says so.

`it https on` refuses before it changes anything in Tailscale where a Funnel stands in the way:

- **`funnel_public`: "Tailscale Funnel makes It public on port …, so https was not turned on."** The message names the port, and its hint the `tailscale funnel` command that turns that Funnel off. Run it yourself, or stop the `tailscale funnel` command that keeps a Funnel up in the foreground, and run `it https on` again.
- **`funnel_unconfirmed`: "A Tailscale Funnel forwards to a place that may be It, and It cannot tell whether it is."** A Funnel forwards to one of It's ports at a name that the system looks up, or in a form It cannot read. `tailscale funnel status` says where. Turn it off if it may reach It, or have it forward to another port.
- **`tailscale`: "Tailscale said what it serves in a form It cannot read."** `tailscale serve status --json` printed something It could not read as Tailscale's settings. `tailscale serve status` shows what Tailscale serves, and a newer It may read it.

Once it has set its two entries up, `it https on` asks Tailscale once more:

- **`funnel_unconfirmed`: "It could not confirm that no Tailscale Funnel makes It public, so it took away what it had just set up in Tailscale and did not turn https on."** Tailscale did not answer in time, or answered in a form It cannot read. It took away the two entries it had just made, where Tailscale still served them as It had set them up, and nothing else. An entry another program changed in the meantime is left as that program has it. Run `it https on` again once `tailscale funnel status` answers.
- **`tailscale`: "It could not take away what it had just set up, so Tailscale may still serve https for It on port …"** Tailscale would not take away the entries It had just made, or would not say what it serves, so It could not tell that they were still its own and left them. It's settings do not say https is on. Run `it https on` again once Tailscale answers, which finishes setting it up, or `it https off`, which takes the entries away.

## A bare `it` on Windows that speaks of a Describe block

In Windows PowerShell, `it` typed where It's folder is not on the PATH does not run It. Windows comes with Pester, a test framework that has a command of its own called `It`, and PowerShell reads names without regard to capitals, so it runs that one, which answers "The It command may only be used inside a Describe block." Nothing is wrong with It when you see this, and nothing was run.

It happens in a terminal or an app that was open before It was installed, because a program keeps the PATH it started with. The install script puts the folder on the PATH of the PowerShell it runs in, so the window you installed from is not one of them, unless Pester's command had already been used in it. Open a new terminal, or start the app again, and `it` is It. Until then, the program's whole path runs It anywhere: `& "$env:USERPROFILE\.it\bin\it.exe" status`. Typed as `it.exe`, the name is never taken for Pester's command, and where the folder is not on the PATH PowerShell says plainly that there is no such command.

An agent in an app that was open before the install is in the same place, since the app runs each of its commands with the PATH it started with. Setup names the program by its whole path in the commands it gives an agent on Windows for that reason, and the skill tells agents to run `it.exe` there. An agent that reports the Describe-block error ran a bare `it`: tell it to use the whole path, or start its app again.

## The Windows command is missing after an interrupted update

If an install or update was stopped while it was replacing `it.exe`, run the install command again. That restores the command without removing your pages or settings. Do not choose a program from the files named `it.old.*.exe` yourself.

A service registered by this version can restore the exact previous program recorded by an interrupted install or update. It checks the writer's process number and creation time, so an unrelated process that later receives the same number does not prevent recovery. Once the writer has stopped, it checks that the file matches the recorded checksum before giving it the `it.exe` name again. It leaves a program already at that name alone. A missing or unreadable record, or a file that does not match it, needs the installer again.

An older service launcher has no recovery step. Once the command is available, run `it service install` to refresh that launcher. A terminal command cannot repair its own missing executable, and a computer with no background service also needs the installer run again.

## Public addresses after upgrading from 0.1.36

A 0.1.36 machine with `it network on` could be reached at a public address. After upgrading, that setting allows private networks only. To restore access through a public address, run `it network internet` on that machine.
