# Whether what the user does arrives by itself, and how to wait for it

`it create`, `it update` and `it tour show` print `arrives` for the conversation they run in, and `it status` prints it as well. Do what its `next` says:

- **`"byItself": true`, `"via": "addon"`**: It's add-on is listening in this conversation, and what the user does arrives as a message that begins `[It]`. End your turn, and do not wait.
- **`"byItself": true`, `"via": "t3"`**: a thread of T3 Code holds this conversation, and T3 Code puts what the user does into the thread, whether or not the add-on runs there. End your turn, and do not wait.
- **`"byItself": false`**: nothing arrives by itself, and `next` says why. In a Claude Code conversation that was already open when It's add-on was installed, it gives you a sentence to tell the user word for word, unless you have told them already: to type /reload-plugins in this conversation, or, in a Claude Code too old for that, to start a new one. Say it as it stands, and wait for what they do until then.
- **`"byItself": "unknown"`**: It cannot tell, as where its connector could not be asked, where T3 Code is running and has not said whether one of its threads holds this conversation, or in Hermes, whose add-on is let speak in some places only. In Hermes a message arrives by itself in the plain `hermes` terminal. In Hermes's TUI and its desktop app it arrives only in a Hermes later than 0.21.5, once the user has allowed it there, and in its messaging gateway it never does. Wait for it.
- **No `arrives` at all**: It cannot tell which conversation you are in. Wait for it, and name the page with `--id`.

If you once ended a turn expecting a message and none came, wait from then on, whatever `arrives` said.

`it status` says more of how It stands. In `harnesses`, your harness has `"addon": "connected"` or `"outdated"` where It's add-on is in it, and `connector` has `"ok": true` and neither `"unfit"` nor `"unchecked"` where the connector runs. Both are needed, and neither is proof that a message will reach this conversation: they say that the add-on is installed and that the connector is up, and `arrives` is what says whether this conversation hears it. With `"needs_approval"`, the `detail` beside it says what the user still has to do. `"outdated"` is an app that runs an earlier build of the add-on than the one It installed: it still takes clicks, and `runtime.detail` says that restarting the app loads the new one. `"incompatible"` is an app whose loaded add-on cannot take clicks from this It, because it speaks another delivery API or the app lacks what it needs: tell the user what `runtime.detail` says. Claude Code with `"proxied": true` beside it was started, as far as `it status` can tell from the environment you share with it, with a proxy that keeps its add-on from asking It anything: tell the user what `it status` says to do. Where `connector` has `"unfit"`, this machine joined an It of a version it does not work with, and nothing done on a page is handed to any agent here until the machine it names is updated: tell the user what it says, and do not count on a message or on `it wait` meanwhile. `"unchecked"` means that It has not yet been able to ask, which is the same for now: nothing is handed over until it has.

It also listens for at most 40 conversations on one machine at a time, the ones it heard from most recently. Where the user has more than that open, a message for one of the others does not arrive by itself until that conversation is among the 40 again.

Where `arrives` says to wait, wait for it: `it wait --id deploy-plan` blocks until the user acts on that page, prints the action and exits. Where several things were waiting they are printed together, one JSON object on a line each and at most 50 at once: read every line, and where 50 came, run it again, since more may be waiting.

- **Without `--id`** it waits for an action on any page this conversation made. That needs your harness to tell `it` which conversation this is. Where it does not, the command is refused, and you must name the page with `--id`.
- **`--timeout <seconds>`** is for a harness that stops a command after a couple of minutes: `it wait --id deploy-plan --timeout 100`. When the time is up it prints `{"timedOut": true}` and exits with status 0. Nothing was lost and nothing has happened yet: run it again. Where It could not be reached to say so, the command ends with an error and a status other than 0 instead: that is not a wait in which nothing happened, so check `it status` before you wait again.
- **`--follow`** goes on printing actions, one JSON object on a line each, and does not exit after the first.
